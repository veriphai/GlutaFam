# Mini-Activity Game Builder — a living playbook

Turn a brief + raw art into a polished, self-contained interactive activity for
this app. **The methodology below is fixed; the activity type and the tech are
chosen per brief — never assume a specific mechanic.** Build Satellite (a
drag-and-assemble Flame game) is the first worked example, not the template.

> ### ⛔ Follow the PRD — do NOT copy the example's feel
> The worked examples teach **methodology and architecture only** — pipeline,
> module structure, the reusable code patterns. They are **not** a reference for
> *what interactions, animations, effects, sounds, copy, meters, or visual feel*
> a new activity should have. **Every interaction and every animation must
> replicate exactly what THIS activity's PRD + storyboard specify** — its scenes,
> its named effects, its sequence, its timings, its tone. If the PRD describes a
> specific animation beat-by-beat, implement that beat-by-beat; never substitute a
> generic version or default to Build Satellite's mechanic/effects/meters just
> because they already exist. Reuse *plumbing*, author *behaviour from the PRD*.
>
> ### 🎨 When visual mockups are provided, THEY are the visual spec
> Per-screen mock images (a storyboard sheet or individual frames) define the
> *look*, not just the mechanics: the **background, element placement, mascot
> pose+position, panel framing, button shape/colour/label** of each screen.
> Building something that merely *works* but looks different from the mock is a
> miss — the mock is the **acceptance criterion**. Match each screen's
> composition first, then tune to it. (Earth Detective: the intro + tutorial
> were rebuilt 2–3× because they were "totally different from the mock".)

> This skill is meant to **grow**. Every new activity should fold its reusable
> patterns, new gotchas, and any new implementation approach back into this file
> and `reference/examples/`. See "Keep this skill growing" at the end.

Output: a module under `lib/screens/missions/<activity_id>/`, wired into the app
(reached from a card/CTA), with cleaned assets under `assets/images/<activity_id>/`.

## Inputs (ask for any that are missing before building)

| Input | What it is |
|---|---|
| **Sprite images** | The art: base/scene, interactive elements, effect overlays, mascot. Often AI-generated with **baked-in / checkerboard backgrounds**. |
| **Storyboard** | Ordered scenes/steps: what the child sees and does, in order. |
| **PRD** | Goal & learning objective, the core mechanic, the elements, win/lose conditions, rewards (XP/badge), any score/meters, mascot personality & tone. |
| **Claude prompt** | Extra build-specific instructions for this activity. |

If the storyboard or PRD is missing, **ask for it** — don't invent the learning
goal, mechanic, or win condition.

## Pipeline

### Phase 0 — Intake (understand the activity; don't assume the mechanic)
- Collect the inputs; pick a short `activity_id` (snake_case).
- Derive the **activity type** from the PRD/storyboard. It is open-ended — e.g.
  assemble/build, sort-into-groups, sequence/order, match pairs, trace/draw,
  simulate/experiment, navigate/explore a scene, branching decisions, rhythm/timing,
  or something new. Let the brief decide; do not force it into a known mechanic.

### Phase 1 — Asset prep (universal: always verify transparency)
AI-generated sprites frequently have **no real alpha channel** — the "transparent"
background is a flattened grey/white checkerboard that renders as solid squares.
1. Check: `sips -g hasAlpha -g pixelWidth -g pixelHeight "<image>"` → `hasAlpha: no` (or a visible checkerboard) must be fixed.
2. Fix + trim + downscale with the bundled tool (flood-fills the background from
   the **borders** so enclosed light art — a white robot, bright cores — is preserved;
   a global colour-key would punch holes in it):
   ```bash
   # single image, in place, with a dark-bg preview to eyeball the cutout
   python3 .claude/skills/mini-activity-game/scripts/strip_bg.py "<image>" --preview
   # batch a folder into the asset dir, mobile-safe sizes
   python3 .claude/skills/mini-activity-game/scripts/strip_bg.py \
     --src "~/Downloads/<activity>_sprites" --out "assets/images/<activity_id>" --target-long 512 --preview
   ```
   - Always open the `*_preview.png` files and confirm nothing got eaten.
   - Real interior cut-out (e.g. a camera bay)? add `--min-hole-area 12000`.
   - **Effect/glow overlays** (rings, flashes, signal waves, flames): for *ring/halo*
     shapes add a smaller `--min-hole-area ~2000` to clear the enclosed faint grid,
     but leave *solid bright cores* (flash/flame) intact. Render all of these with
     **additive blending** (`BlendMode.plus`) in the engine — any faint residue then
     disappears against the dark stage.
   - Full-bleed background art that just fills a frame needs no transparency.
3. **Asset-kit realism (don't assume a clean layered kit):** AI-generated element
   sprites are usually independent **single-angle hero renders** with slightly
   mismatched perspective, and any `*_slot_empty` / alternate files may be whole
   different renders rather than overlay decals. So: pick **one canonical base/scene**
   and **overlay** the elements at tunable anchors (Phase 4); ignore off-angle
   alternates. Minor perspective mismatch reads fine at kid-scale with juicy effects.
   Sizes vary wildly → never hardcode element sizes; derive from the base (Phase 4).
4. Declare the dir in `pubspec.yaml` (`flutter: assets: - assets/images/<activity_id>/`), `fvm flutter pub get`.
   Folder asset declarations are **not recursive** — declare each subfolder you add.
5. Centralise paths in one **asset registry** (`config/asset_paths.dart`) — see the
   example for the dual Flame/Flutter path flavours. Never hardcode filenames elsewhere.

### Phase 2 — Plan (confirm with the user before coding)
From the PRD + storyboard derive and write a short plan: the steps/scenes, the
interactive elements + their correct outcomes, feedback for right/wrong, win/lose
conditions, score/meters, rewards, and the mascot's voice. Present it; adjust per
feedback before writing Dart.
- **Transcribe the PRD's animation storyboard literally.** Capture each scene's
  named effects, exact sequence, timings, triggers, and copy as a per-element
  checklist to implement against. This is the spec — do not paraphrase it into a
  generic flow or borrow another activity's beats.
- **Transcribe the VISUAL mock per screen too** (separate from the animation
  storyboard). For each provided mock frame, list: which background, element
  placement, mascot pose+position, panel framing, button shape/colour/label.
  Build to that composition — it's the visual acceptance criterion, not loose
  inspiration. (Earth Detective.)

### Phase 3 — Pick the implementation approach (fit the mechanic)
Choose the **simplest** tech that delivers the intended feel:

| Approach | Best for |
|---|---|
| **Pure Flutter** (widgets + `CustomPainter` + `AnimationController`) | taps, sorts, sequencing, matching, forms, light animation; seamless app integration, zero extra deps |
| **Flame** (game engine) | a "stage" with spatial drag/drop, real-time motion, many entities, optional follow-camera. Build Satellite uses Flame on a **fixed** stage (components on the game root, no camera) |
| **Rive** | designer-authored animated/interactive scenes driven by state machines |
| **forge2d / physics** | collisions, gravity, momentum, free movement |

Document the choice + why. (If a brief needs an approach not listed, use it and
add a row here.)

### Phase 4 — Architect & implement
Build a **self-contained, config-driven** module under
`lib/screens/missions/<activity_id>/`: keep *content* (catalog, layout, steps,
copy) in `config/` + `state/`, separate from *generic logic*, so the next
activity is mostly new config + assets. Reuse the app design system
(`careerTheme.dart`, `careerCommon.dart`, `cosmicBackground.dart`). See
`reference/examples/` for a concrete layout.
- **Screen shell:** put the background + content + overlays as **`Positioned.fill`**
  layers of a `Stack` (see gotcha) so the `Column`/`Expanded` is height-bounded and
  the bottom controls never get pushed off-screen.
- **Spatial anchors:** express element positions as **factors of the base rect**
  (not pixels). They'll be eyeballed from the art — **budget a live tuning pass** on
  device; keep them all in one config map so a nudge = editing one number.
- **Entry wiring:** thread an optional `onTap`/callback **param through the existing
  card/CTA widget** and navigate from there — don't hardcode navigation inside the
  shared card. (e.g. the career-home profession card + hero "Continue" CTA push the
  activity screen.)

### Phase 5 — Polish
**First implement the PRD's storyboard exactly** — each element's specific
deploy/feedback animation, in the order, with the effects and timing the PRD
names. The toolkit below is the *generic polish layer* you add on top (and only
where the PRD doesn't dictate something more specific); it is never a substitute
for a PRD-specified beat, and never a reason to reuse another activity's effects.

Generic polish layer: right/wrong feedback, `HapticFeedback`, SFX (reuse
`jumpSound.mp3`, `correct_answer.mp3`, `incorrect_answer.mp3`, `levelComplete.mp3`),
entrance/idle animation, reward popup on completion, and an idle-hint after inactivity.

- **Drag-based mechanics (mobile):** use an **immediate** `Draggable` — **never
  `LongPressDraggable`**. Hold-to-drag was explicitly rejected as wrong for a
  kids' mobile app. If the items live in a scrolling list, give the `Draggable`
  `affinity: Axis.vertical` so a *horizontal swipe scrolls the list* while a
  *vertical drag grabs the item instantly* (orthogonal axes → no conflict). Use
  `dragAnchorStrategy: pointerDragAnchorStrategy` and centre the feedback under
  the finger (`Transform.translate(-half)`).
- **Inventory / list of items:** a horizontally **scrolling** list of
  comfortably-sized cards. Don't shrink many items to cram them into a fixed-width
  row ("don't try to adjust everything in this little space"). Auto-scroll the
  active/required item into view at each step.
- **Make flat sprites feel 3D:** wrap the stage in a subtle perspective tilt
  (the reusable `tilt_view.dart` pattern — idle figure-eight sway + drag-to-tilt
  that springs back, ~±10°). Keep it small so drop coordinates stay accurate.
  ⚠️ A single-angle 2D sprite **cannot truly rotate/orbit** (no top/bottom/back
  data) — that needs a real 3D model (glTF via `model_viewer_plus`/`flutter_3d_controller`)
  or a pre-rendered **turntable** sprite sequence. Offer the fake tilt for premium
  feel now; reserve real 3D for a post-build "inspect your creation" reward.

### Phase 6 — Verify
- This repo uses **fvm** — always `fvm flutter …` / `fvm dart …` (bare `flutter`/`dart`
  are not on PATH).
- Analyze the module: `fvm dart analyze lib/screens/missions/<activity_id>` → expect
  **only** `file_names` info lints (this repo uses camelCase filenames — match it).
  - ⚠️ `fvm flutter analyze <pathA> <pathB>` with **multiple paths crashes** the analysis
    server (exit 64) — use **`fvm dart analyze <single dir>`**.
  - `fvm dart analyze lib` reports ~hundreds of **pre-existing errors** in unreferenced
    experimental files (e.g. `interactive_table_scene.dart`, `journey_card.dart`) that
    are not in the app's compile graph — they're **not yours**; filter to your paths.
- Compile the full graph: `fvm flutter build apk --debug` (validates everything reachable
  from `main` compiles; the artifact appears at `build/app/outputs/flutter-apk/app-debug.apk`).
- Run in Chrome (`fvm flutter run -d chrome`; full restart `R` after asset/pubspec changes);
  manually test the core interaction **and confirm bottom controls are visible on a TALL
  (mobile) viewport**, not just a short/desktop window.
- **Plan a live visual-QA loop WITH the user — early.** You can't interactively play the
  activity; analyze + a debug build only prove it *compiles*. Real issues surface only on
  device at real sizes/brightness — additive blowout over bright art, narrow-icon
  off-centering, baked-card mismatch, "make it bigger". After it compiles, hand it over for
  a screenshot pass and expect **many rounds of per-screen, mock-driven tuning** (Earth
  Detective ran ~20 visual iterations — bg swap, mascot swap, panel polish, scanner/zoom UX,
  asset re-cropping); the mock is the acceptance criterion. Don't claim visual/gameplay
  correctness you haven't seen. Pure-Flutter UI changes hot-reload (`r`); asset/pubspec or
  Flame-construction changes need a full restart (`R`); a **new asset file needs a full
  re-run** (see gotcha).
- **Re-run `fvm dart analyze <dir>` immediately after any widget-tree restructure** (swapping
  `Expanded`↔`SizedBox`/`LayoutBuilder`, rewrapping a `Stack`) — a bracket mismatch is easy to
  introduce and the analyzer pinpoints it instantly instead of a confusing runtime failure.
- **Remote-debug an interaction you can't play:** add a TEMP on-screen readout — a
  `ValueNotifier<String>` on the game surfaced via a `ValueListenableBuilder` overlay — that
  updates on each tap/drag with the live numbers (`canAim`, reticle vs hotspot positions,
  `dist`, hit radius, `HIT=true/false`), plus a **visible hit-zone ring** at the target. One
  screenshot then tells you whether the gesture even fires, whether it's a hit/miss, and
  whether the target lines up — instantly pinpointing "tap not reaching the game" vs
  "coordinates off" vs "logic-after-hit crashing". Remove it before shipping.
- **Self-verify visuals headless (you CAN screenshot, even drive it) — Playwright on a web-server build.** Don't only hand off blind: (1) write a THROWAWAY entrypoint `lib/_preview.dart` whose `main()` is `runApp(MaterialApp(home: <ActivityScreen>()))` so the activity is the first screen (no in-app navigation); (2) `fvm flutter run -d web-server --web-port 8767 -t lib/_preview.dart` (serves headless, no Chrome window — detach with `( … & )` and poll the log for "is being served"); (3) Python Playwright (`~/Library/Caches/ms-playwright` chromium is usually present): `chromium.launch()` → `new_page(viewport={'width':412,'height':915}, device_scale_factor=2)` → `goto('http://localhost:8767')` → `time.sleep(15)` (CanvasKit + Flame asset load needs real time to paint) → `screenshot()`. To DRIVE it (Flutter web is a canvas, so no DOM selectors): screenshot first, find the button by **pixel colour** with PIL (e.g. scan for the green CTA), then `mouse.click(cx/scale, cy/scale)` — divide by `device_scale_factor` since the screenshot is 2× the CSS coords. This caught + confirmed the fix for an intro-overlay dead-zone bug in one loop. Delete the preview file + kill the server after. Still hand off to the user for device brightness/feel — but land the obvious layout/asset bugs yourself first.
- A debug APK for on-device testing: `fvm flutter build apk --debug` → install via
  `fvm flutter install` / `adb install -r build/app/outputs/flutter-apk/app-debug.apk`. It's
  large + slow (debug); build `--release` once the activity is final.

## Reusable building blocks (toolkit — use what fits)
- **Config-driven content:** catalog + layout/positions + steps as declarative data, separate from logic.
- **State:** a single `ChangeNotifier` owning an **immutable** state object; UI rebuilds via `ListenableBuilder`/`AnimatedBuilder`. No Provider/Riverpod needed for a self-contained activity. (Keep the `GameWidget` OUTSIDE the rebuilt subtree — build it once so Flame isn't re-attached every frame.)
- **Flutter ↔ Flame bridge** (Flame stage + Flutter drag sources): wrap the `GameWidget` in a `DragTarget`; on `onMove` feed the pointer to a `updateHover()` (lights the target), on `onAcceptWithDetails` convert the global offset to game-local (`renderBox.globalToLocal`) and hand it to the game's placement method. The drag source uses `pointerDragAnchorStrategy` so `details.offset` == the pointer.
- **Immediate drag inside a scroll list:** `Draggable(affinity: Axis.vertical)` — vertical drag grabs, horizontal swipe scrolls. Never `LongPressDraggable` for a kids' mobile UI.
- **Scrolling inventory:** a horizontal `ListView` of comfortable cards; auto-scroll the active item into view per step (a `ScrollController` + post-frame `animateTo`).
- **Fake-3D tilt (`tilt_view.dart`):** a perspective `Matrix4` (`setEntry(3,2,…)` + `rotateX/rotateY`) driven by an idle sway + a drag that springs back. Makes a flat single-angle sprite feel solid; reusable for any stage.
- **Native in-stage aiming (Flame):** when the drag happens INSIDE the stage (not from a Flutter tray), handle gestures with a **full-stage gesture-catcher component** — a `PositionComponent with TapCallbacks, DragCallbacks` whose `containsLocalPoint => true`, added on top — and forward `event.canvasPosition` / accumulated `event.localDelta` to the game. This reliably handles **both tap and drag**; prefer it over the game-level `PanDetector`/`TapDetector` mixins (`PanDetector` alone misses taps, and `TapDetector` is **deprecated** and conflicts). Magnetic-ease the reticle toward the hotspot within a forgiving radius; swap to the "active" sprite when near. **Spawn the reticle OFFSET from the target** (a random distance away), not on it — otherwise releasing without moving auto-wins; aiming should be a skill. **Bias the hit target onto the object body** (a touch above the sprite centre) since problem sprites carry shadow/ground below their middle. Size the reticle/target from the **base (un-zoomed)** dimension (see gotcha) so they don't balloon when the focus zooms.
- **Render icon-font glyphs INSIDE the Flame canvas** (the premium-symbol path): a small `IconFx` component paints an `IconData` via `TextPainter` (`style: TextStyle(fontFamily: icon.fontFamily, package: icon.fontPackage, fontSize: …)`, text `String.fromCharCode(icon.codePoint)`) with a pop-in scale + soft glow. Works for Material Icons AND premium font packs (`phosphor_flutter` etc.) since they're font-based. **Prefer crisp icons over poor AI effect sprites** for simple symbols (location pin / wifi / check). (Nuances "no emoji in Flame": emoji no, **font-glyph icons yes**.) Allow a separate `glowColor` so a white glyph can carry a coloured halo.
- **Dim-base + emerge-and-zoom focus presentation:** to spotlight the active element without a real camera — dim the base scene (its own sprites), then present the element **enlarged + centred**, animating it *rising from its real position on the base and zooming in* (component `MoveEffect`+`ScaleEffect`, all in one coordinate space). Reusable for any "bring this part of the scene forward" beat.
- **Programmatic beam / route / path:** if an effect sprite is vertical-only (beams) or a whole-scene render (route islands), draw it programmatically instead — a multi-pass additive line (outer glow / mid / white core) for beams, a self-drawing polyline (progress 0→1) for routes. (Endpoint glow sprites still used.)
- **Composited scene from a bare base + props:** one config map (e.g. `earth_layout.dart`) holds the base placement + each prop's `center`/`width` factor; it drives BOTH the engine composite and any Flutter label overlay. Expect heavy live tuning when props are mini-islands.
- **Scene state-machine shell (multi-scene activities):** for activities that are a *sequence of full-screen scenes* (story intro → test → play → challenge → success → teaser), drive them with an `ActivityScene` enum on the immutable state and route with an `AnimatedSwitcher` keyed by scene (`KeyedSubtree(key: ValueKey('sceneName'))` so each scene type animates in/out but doesn't re-mount on every `notifyListeners`). A sub-state that stays on the same screen (e.g. `wrongAnswerFeedback` on the challenge) shares the **same** key as its parent scene so it doesn't remount. (How Much Can You See.)
- **Flame stage as ONE scene of a Flutter activity:** when only one scene is a rich animated "stage" and the rest is Flutter, build the `FlameGame` + `GameWidget` **once** in the shell's `initState` and pass the cached `GameWidget` *instance* into that scene — reused across rebuilds → same Element → Flame is never re-attached. The game listens to the same `ChangeNotifier` and only animates while its scene is active. Keep 1-D/snap drags (a height rail) in Flutter where labels are easy; reserve Flame for the layered motion.
- **Controller-driven Flame (zero in-stage input):** the inverse of in-stage aiming — when ALL controls are Flutter (buttons/slider), the game owns no gestures. It adds one `controller` listener and a `switch(scene)` against a cached `_lastScene` fires each transition's visuals **once**; intra-scene notifies (e.g. slider moves) fall through to a live-preview update. The game calls the controller back at animation beats (`onDone`) to advance the machine. (Orbit Launcher.)
- **Scripted trajectory (authored curves, no physics):** a reusable dashed-polyline component (`setPath`/`progress`/`color`, two-pass additive glow+core) + a generic `_FlightRunner` (drives 0→1 over duration·curve, `onStep`/`onDone`) that samples the path (`pointAtFraction`) to move a sprite **in lock-step with the revealed dashes**; build curves from `_bezier`/`_arc` helpers off live geometry, and a separate angle-sweep runner for a continuous loop. Reuse for any "object travels an authored path while a trail draws in" (orbit, escape, crash arc). A live faint preview = the same renderer at low opacity rebuilt on input change. (Orbit Launcher.)
- **Two-framing crossfade backdrop:** one component holding two representations of the same subject (e.g. a bottom "horizon" band + a centred "globe") that crossfades opacity (+ small scale) between them, AND is the single geometry source of truth the rest of the game reads. Cheap way to deliver a "zoom-out reveal". (Orbit Launcher.)
- **Banded-outcome parameter sim:** one input (a slider 0–100) → `outcomeFor(int)` thresholds are the entire "physics"; per-band colour/curve/copy live in config and retune trivially. (Orbit Launcher.)
- **Unify the shared action across divergent outcomes; branch at the boundary, not the start:** when one action (a launch) leads to several outcomes that play out in *different framings*, play the **shared leg identically** for every outcome (same thrust, same starting framing, same fly-up) and only crossfade to the destination framing + diverge **at the boundary**. Don't reveal the destination framing or fire its effects before the shared leg finishes. Enabling insight: **a fixed Flame stage is ONE absolute screen-coordinate space — "framing" is just which backdrop sprite is shown** — so the actor + its trajectory cross the boundary continuously while you merely crossfade the background underneath. (Orbit Launcher: every speed launches up from the pad in horizon framing, then at the boundary the globe fades in and the orbit/almost/escape arc continues.)
- **Match direction at a trajectory handoff:** when a launch leg hands off into an orbit/arc, lean the launch curve the way the next motion goes, choose the arc's spin (CW/CCW) to continue that heading, and set the continuing arc's **start angle = the boundary angle** — otherwise the motion visibly reverses at the seam. (Orbit Launcher.)
- **Flex-to-fill hero tiles/cards (for "make it bigger"):** size showcase tiles/cards off the *available width AND height* — `Expanded` rows of `Expanded` tiles, each tile an `Expanded(Image, fit: BoxFit.contain)` + label — rather than fixed px. The icons then render as large as the slot allows, the layout stays responsive, and "make it big / show 2-per-row" becomes a one-number change (columns-per-row + the panel's slot). Users ask for this repeatedly. (How Much Can You See: Scene-1 hologram + challenge grid.)
- **Reversible scene flow (per-scene CTA callbacks):** route every scene through ONE `switch(scene)` and inject each scene's forward action as a callback (`onContinue`/`onExit`/`onNext`) rather than hardcoding `Navigator`/transitions inside scenes. Bypassing or reordering scenes ("skip the bridge + teaser, exit right after the MCQ") is then a one-line change to which callback a CTA fires, and skipped scenes stay in the code for easy restore. (How Much Can You See: success → exit, bridge/teaser kept but unreached.) Flow choices also **reverse after the user sees them on device** (Earth Detective: a mission-select hub → linear auto-advance like Restore Earth), so build the flow reversible and re-confirm the between-level transition once it's playable.
- **No-op analytics:** an `analytics.dart` implementing the spec's events as debug logs, with calls wired at the real points — swap the bodies for a real tracker later without touching callers.
- **Activities hub + nav entry:** an `ActivitiesScreen` listing every activity; reach it via an optional `onSelect(label)` callback threaded through the existing bottom nav. New activities = one entry in the hub.
- **Resolution-independent layout:** define positions as **factors relative to a base rectangle**, not absolute pixels.
- **Feedback kit:** SFX + haptics + mascot helper + reward popup (reuse the `confetti.json` Lottie) + idle-hint timer.
- **Pure-Flutter tray→card dispatch (no Flame):** when the mechanic is "drag a tray card onto a target card" + sprite-overlay effects (fade/scale/rotate/pulse), DON'T reach for Flame. Wrap the target in a `DragTarget<T>`: `onMove`→light the zone (whole-card hover is fine, kid-friendly, no GlobalKey math), `onAcceptWithDetails`→`controller.resolveDrop(data)`. Drops OUTSIDE the card never fire accept → "drop outside = no penalty" is free. Tray cards are immediate `Draggable`s (`pointerDragAnchorStrategy` + feedback centred via `Transform.translate(-size/2)` + a trail sprite). The **controller owns discrete state, the scene owns timing**: the scene listens and **diffs cached values** (`_lastPhase/_lastIndex/_lastToken`) to fire `AnimationController`s, chaining via status listeners (snap→effect→markSolved); plain 0..1 values feed a timing-stateless card widget. Fire one-shot transients (wrong pulse) by **bumping an int token** in state, not a bool you must reset. (Choose the Right Satellite.)
- **Runtime aspect map (avoid `ui.Image` decode):** to place factor-anchored sprite layers precisely without async decoding, capture each sprite's intrinsic w/h at asset-processing time into a `const Map<String,double>` and compute `h = w/aspect`. One `crsLayer(scene, centerFactor, widthFactor, aspect, child)` helper then places every layer/effect/dock identically. (Choose the Right Satellite.)
- **Controller-owns-geometry (continuous-logic activities):** when the core logic is *continuous* (an angle × range × battery → state computed every frame), bend the usual split — let the **controller own the scene geometry too**. The game reports the stage size ONCE (`setStageSize`), then each frame calls `controller.tick(dt)` and RENDERS from controller pixel getters (computed from factor anchors × size), feeding back ONLY the in-stage drag. All thresholds + phase logic stay in one testable place; the game is a pure renderer+input. Derive the mid-game phases from the live signal state (`locked→dataLocked, strong→checkPower, else→waitForRange`) so the child can slip back and forth without penalty. (Signal Rescue.)
- **Controller-driven sim + token-diff FX (continuous resource game, zero in-stage input):** for a real-time *resource-management* sim (battery × orbit-zone × solar × tool-drain every frame) where ALL controls are Flutter dock buttons — combine **controller-owns-geometry** (game reports stage size once, ticks `controller.tick(dt)`, renders purely from controller pixel + **presence-fade getters**) with **token-diff FX**: state carries bump-counters (`captureToken/sendToken/chargeBurstToken/warnToken`), the game caches last values and fires a one-shot `_spawnEffect` when one changes. The game owns no gestures and no logic; events flow controller→game via incremented ints, never callbacks. Pair with **presence getters** (`shadowFactor/sunPresence/cyclonePresence` = smoothstep ramps off orbit progress) so the WORLD fades in/out around a roughly-centred actor (matches a mock where the actor stays central and the *context* changes) instead of flying it round a big loop. (Power Balance.)
- **Guided-orbit HOLD → free flow (guided-to-free pacing):** drive a guided tutorial on the SAME continuous clock as free play by **freezing the orbit at a per-phase hold point** until the child acts: `holdAt = switch(phase){ solarTutorial→holdSunlight, firstCapture→holdTarget, firstTransmission→holdGround, _→null }`; the clock eases toward `holdAt` then stops, and `null` (shadow tutorial onward) lets it wrap freely. ## Universal gotchas (carry every time)
- **CLAMP a large `dt` in the game loop — never DROP it.** The common guard `if (dt > 0 && dt < 0.1) controller.tick(dt)` *silently freezes all beat/flow logic* whenever frames are slow: a backgrounded/throttled tab — and **headless Chromium for self-screenshots** (its rAF is throttled, so every delta exceeds the threshold) — delivers big deltas the guard discards, so sim time never advances. The intro line shows but nothing ever progresses, the Send/Continue CTA never appears, and geometry that depended on a not-yet-final `onGameResize` reads half-size. Symptom in a screenshot: bubble stuck on the framing line + wrong proportions. Fix: `if (dt > 0) controller.tick(dt > 0.05 ? 0.05 : dt);` — clamp the spike to a steady step so logic keeps moving (also kinder to a real device's resume-delta). (Leaky Bucket: cost an entire screenshot loop chasing a "geometry bug" that was a frozen game loop.)
- **A clean kit means SKIP `strip_bg.py` — don't flood-fill working alpha.** Some packs arrive already cut out: `hasAlpha: yes` AND the four corners are α=0 AND coverage is a sane 25–75%. Running the border flood-fill then *erases white art* (white clouds, a `*_white` overlay, a starburst flash, a white robot body) because they read as bright-neutral background. Verify with a corner-alpha + transparent-% probe; if it's already clean, just **trim-to-alpha-bbox + downscale** (and JPEG the opaque full-bleed bg). The flood-fill is only for baked checkerboards (`hasAlpha: no` or a visible grid). (Choose the Right Satellite: clean kit, 39MB→9.7MB trim-only.)
- **Transparent corners are NOT proof of a clean interior.** AI art often bakes "fake transparency" (a checkerboard) into the **opaque RGB** of beams / halos / glow fills — the corner-alpha + coverage probe passes (corners are α=0, coverage sane), yet the interior renders a visible checker in-app at full opacity. A pixel-alpha check will *never* catch it. Always **composite the sprite on a dark bg AND zoom into the interior + every effect/glow region** before trusting it. (Earth Detective: the Earth-hologram beam AND the deforestation overlay both shipped opaque baked checker the "clean kit" probe missed; fixed one by circle-masking the globe, the other by colour-keying out the bright neutral interior.)
- **Mask to the subject's shape; don't rectangular-crop a round/irregular subject — and re-derive aspect after.** Removing a baked artifact (a beam/stand/checker below a globe) with a rectangle crop slices a **chord through anything non-rectangular** (Earth Detective: cropping the hologram at 62% height gave the globe a flat bottom). Detect the subject's true bounds and apply a **shape/alpha mask** (we found the globe's centre+radius and used a feathered ellipse mask, then trimmed bbox). And note: ANY reprocess (crop / mask / resize) **changes the sprite's aspect → update the runtime aspect-map entry AND every size/position that assumed the old ratio** — we hit overflow + a flat-bottom + misplaced overlays twice from a stale aspect.
- **Transparency:** always `sips -g hasAlpha`; fix baked/checkerboard backgrounds via flood-fill-from-border, never a global colour key. The checkerboard is two near-neutral light-grey shades (~242 & ~254) → detect background as *bright AND low channel-spread*, keep only the **border-connected** region.
- **Dark-checkerboard glow sprites strip to 0%.** `strip_bg.py`'s default `--min-bright 228` only catches *light* checkerboards; some glow/effect sprites (rings, sparkle bursts) ship on a *dark* grey checkerboard, so the default pass removes **nothing** (`0.0% transparent`). A 0.0% result on a glow IS the signal. Fix: `--min-bright 24 --neutral-tol 34`, then add `--min-hole-area` (e.g. `5000` ring interior, `1200` sparkle blob) to clear the enclosed neutral regions the border flood-fill can't reach. (Orbit Launcher: `orbit_ring_glow` + `success_sparkles`.)
- **Shell layout:** content layers inside a `Stack` must be **`Positioned.fill`** (not bare/non-positioned). A loose Stack child can leave a `Column`/`Expanded` height-unbounded so the **bottom controls get pushed below the fold on tall (mobile) viewports** — a real bug we hit. Always test a tall viewport.
- **`AnimatedSwitcher` shrinks a full-screen overlay to its content (the "dead-zone" bug).** Its default `layoutBuilder` wraps children in a `Stack(fit: StackFit.loose)`, so a full-screen scrim/overlay (intro start page, success/failure scrim) gets LOOSE constraints and a `Container(color:)` sizes to its child instead of filling — leaving a gap where the layer BELOW (the bottom cluster, a bright bg) bleeds through as a flat dead band. Fix: pass a `layoutBuilder: (cur, prev) => Stack(fit: StackFit.expand, children:[...prev, if (cur!=null) cur])` so children fill. AND: a **semi-transparent** intro scrim (0.8α) lets the busy gameplay scene + the Mission Control card bleed through and look broken — make the start page **near-opaque** (≈0.96 gradient) for a clean premium page, and **hide the bottom cluster while `!isPlaying`** (an `AnimatedOpacity`+`IgnorePointer` on the whole cluster) so it never sits behind the intro/success/failure overlays. (Power Balance.)
- **Never resize the Flame stage mid-activity.** If the `GameWidget`'s box changes size, anything positioned as a *factor of the stage size* shifts — so an element placed at the old size and a target recomputed at the new size **drift apart** (Restore Earth: showing the power panel shrank the stage → the reticle/target slid off the car). **Reserve constant heights for all bottom UI and reorder/fade slots instead of changing total height** (e.g. swap the mission-panel ↔ power-panel order between intro/play but keep both heights reserved). One stable stage size → placement stays aligned on every screen.
- **A fixed-aspect media panel (e.g. a 4:3 image) inside an `Expanded` portrait box letterboxes — decide centred-vs-hug deliberately, reserve headroom, and align overlays to the CONTENT rect.** We flip-flopped (too-empty Expanded → too-short fixed → Expanded again). Pick one and state why: *centred-in-Expanded* (card fills the area; the letterbox reads as breathing room) OR *hug-the-content height* (`SizedBox(height ≈ width × imgAspect + headroom)`). If a floating element needs room (a satellite above the image), **reserve a headroom band inside the content-rect math** (top-anchor / inset the image). Crucially, **factor-anchored overlay controls (zoom buttons, BEFORE/AFTER tags) must be positioned relative to the displayed IMAGE rect, not the full stage box** — otherwise they drift: Earth Detective's zoom +/− centred on the whole card and sat too high because the image was pushed down by the satellite headroom (fix = offset the overlay down by that same headroom). (Earth Detective.)
- **Reveal action controls only after the activity starts** — hide the power/tool panel during the intro (fade it in on Start), but keep its height reserved (per the rule above) so revealing it doesn't resize the stage.
- **Synchronous `notifyListeners()` foot-gun.** A `ChangeNotifier`'s notify runs its listeners **synchronously, inline**. If the game listens and a state change makes it remove/replace a component you're about to use right after the notify call, you crash on the stale reference (Restore Earth: a correct hit flipped phase→repairing → the listener removed the reticle → the next line did `_reticle!.position` → null-crash, repair never played). **Capture every value/position you need BEFORE calling the controller method that notifies.**
- **A scene-switched embedded `GameWidget` loses its controller listener on unmount.** If the game adds a `controller` listener in `onLoad` and removes it in `onRemove`, then the instant its scene is switched away the `GameWidget` unmounts → `onRemove` tears the listener down → it's **never re-added** (`onLoad` runs once per game lifetime), so every later state change is silently ignored. (Earth Detective: missions 2–6 all kept showing mission 1's satellite image because the per-mission "load the scene" reaction lived in the dead listener.) When the embed mounts/unmounts across scenes, **drive per-scene/per-mission sync by diffing the controller state inside the component's `update()`** (which runs every frame while mounted) — not via an onLoad/onRemove listener. (Cross-ref "Flame stage as ONE scene".)
- **To recede a scene, dim the scene's OWN sprites** (lower their `opacity`), **not a full-stage scrim** — a scrim also darkens the background and stacks on already-dark art, reading as solid black. (Restore Earth focus mode.)
- **Drag UX:** **immediate** `Draggable` only; for a scrolling list use `affinity: Axis.vertical`. Never `LongPressDraggable`/hold-to-drag on a kids' mobile UI.
- **Don't use baked full-card/full-tile sprites in a grid** — each generated `*_choice_card.png` / `*_tile.png` ships its own frame, padding, and glow, so a row of them looks mismatched (different sizes/insets). Instead **draw ONE card frame in Flutter** (rounded glass + glowing border) and drop just the **subject icon** (the `03_objects` cut-out) inside via `Expanded(Image.fit: contain)` + a Flutter label — every card is then pixel-identical bar the icon. Render right/wrong/hint **feedback as Flutter** (border colour + `BoxShadow` glow + a shake/pulse transform), not baked glow overlays. (How Much Can You See: challenge cards + Scene-1 hologram tiles.)
- **A `Row`/`Column` with `crossAxisAlignment.stretch` in an UNBOUNDED cross-axis renders BLANK (zero-size).** A row of equal-height cards (`Row(crossAxisAlignment: stretch)` of `Expanded` children) collapses to zero height when it sits in a height-unbounded parent (a `mainAxisSize.min` Column inside an `AnimatedSwitcher`/scroll view) — the cards just don't appear, no error. Wrap the `Row` in **`IntrinsicHeight`** (height = tallest child) so stretch has a bound. Symptom: "I tap the step and nothing shows." (Satellite Doctor: the 3 repair-choice cards were invisible until wrapped in `IntrinsicHeight`.)
- **2D ≠ 3D:** a single-angle sprite can't be rotated to reveal other faces — don't promise free orbit. Use the fake `tilt_view` for dimensionality, or commit to a real 3D model / turntable sprite sheet.
- **`ready` is a reserved `FlameGame` member** — naming your own readiness `Completer` getter `ready` throws `conflicting_field_and_method`. Use `stageReady`/`whenReady`. (Same caution as `width`/`height`/`scale`/`center` on `PositionComponent` — don't shadow built-ins.) **`PositionComponent` already has a `center` getter** (absolute centre from position+anchor+size); don't redeclare it (`annotate_overrides`) — just read the inherited one.
- **Relative-import depth in module subfolders:** the screen shell sits at `missions/<id>/` so it imports the house kit as `../../home/career/...`, but files in `<id>/widgets/` and `<id>/scenes/` are ONE level deeper → they need **`../../../home/career/...`**. A wrong depth is `uri_does_not_exist` + a cascade of "method PressableScale/Floaty isn't defined". (Code the Satellite.)
- **Newly-declared assets need a FULL re-run, and a new `Image.asset` needs an `errorBuilder` + bounds.** Adding an asset folder + a `pubspec.yaml` line — **or even just a new file dropped into an already-declared folder** — is NOT picked up by hot reload/restart — especially on **Flutter web**, where the dev server keeps serving the old asset manifest and the file 404s until you stop and re-run `flutter run`. An unbounded `Image.asset` that throws on the missing asset then **cascades into a red error that breaks the whole screen**, and the unbounded intrinsic size overflows the layout. So whenever you add an image: wrap it in a **bounded `SizedBox`** AND give it `errorBuilder: (_, __, ___) => const SizedBox.shrink()` so a not-yet-served asset degrades to nothing instead of taking down the page. (Code the Satellite: the reused kid avatar 404'd on web until a full re-run.)
- **`AnimatedSwitcher` CENTRES its children — content-sized chat bubbles drift away from their speaker.** The default `layoutBuilder` is a `Stack(alignment: Alignment.center)`, so a bubble narrower than the available width floats to the middle instead of hugging the mascot beside it (short lines like "Running: X" show it worst; long lines mask the bug by filling the width). Pass a custom `layoutBuilder` with `Alignment.centerLeft` (or whichever edge the speaker sits on). (Code the Satellite: Orbit's play-phase bubble.)
- **Dart 3 switch — trailing `break;` is `unnecessary_breaks`:** cases no longer fall through, so a `break` as the last statement of a `case` is a lint. End each case with its real last statement (or `return`/`continue`). (Code the Satellite.)
- **`StackFit.loose` top-left hug (the "Tower" bug):** a `Stack`'s non-positioned children get **loose** constraints, so a `Column` inside shrinks to its *widest* child. A card holding a **narrow** icon (a tower) then collapses to that narrow width and the whole content hugs the Stack's top-left — looking off-centre — while cards with **wide** icons fill the card and look fine. The bug is invisible until a narrow icon hits it. Fix: `Stack(fit: StackFit.expand)` + the inner `Column(crossAxisAlignment: stretch)` + `Text(textAlign: center)` so content fills the card and centres regardless of icon aspect.
- **PRD overlays that *veil* the main scene are optional — validate them on the real bright art early.** A spec can call for framing overlays (a scan cone, a "visible-area" ring/vignette) that, rendered over the actual bright scene, just *cover* it (especially additively — see below). Often the scene itself already carries the concept (backgrounds zooming out = "you see more with height"), so the overlay is cuttable. Build it, but test it over the real background ASAP and be ready to drop it on feedback rather than defending it because the PRD listed it. (How Much Can You See: scan cone + view-ring removed.)
- **Effect sprites:** render glow/flash/wave/flame overlays with `BlendMode.plus` (additive) so faint prototype residue vanishes on the dark stage; strip enclosed faint background from ring/halo effects but keep solid bright cores. (Glow-forward *interactive* UI too — marker/rail/nodes/view-circles — keeps a pale matte fringe from the glow's own soft falloff that strip_bg **cannot** remove as background; additive on the dark stage hides it, or place it over a bright background.) ⚠️ **Additive only over a DARK stage.** `BlendMode.plus` ADDS to whatever's behind, so over a **bright** background (sunny sky, green scene) it pushes faint glows/fills straight to opaque white — a "blocking white blob" bug (How Much Can You See: the view-ring + scan-cone over the daylight street). Over bright scenes use **normal alpha** at modest opacity (the fringe is invisible bright-on-bright anyway), or skip the overlay.
- **`update()` vs `Effect` on the SAME field:** a Flame component's `update()` and an `Effect` (Move/Scale/Opacity) that both write `position`/`scale`/`opacity` **fight** — the per-frame `update()` overwrites the effect and the animation never shows (entrance slide-in snaps; fade-in pops). Pick ONE owner per field: either drive that field entirely in `update()` (entrance lerp → idle loop; fade-in/steady/exit opacity envelope), OR leave it to an Effect and never touch it in `update()`. Animate *different* fields with each (e.g. scale via a one-shot `ScaleEffect`, position via `update()`).
- **Zero-duration `EffectController` asserts.** `EffectController(duration: 0)` throws `"Duration must be positive: 0"` — it bites the `animate: false` branch of a show/hide helper (`OpacityEffect.to(target, EffectController(duration: animate ? 0.4 : 0))`). For an *instant* change set the field directly (`opacity = target; return;`), never via a 0-second effect. (Orbit Launcher: crashed on the initial entry setup.)
- **Emitter effects must GROW with the actor, not spawn full-size.** A launch beam / exhaust / trail spawned at its final size pops in wrong. Drive it each frame off the actor's live position (e.g. beam height = pad-to-rocket distance, bottom-anchored at the pad) so it stretches as the actor moves. (Orbit Launcher: launch beam.)
- **Keep celebration bursts OFF the hero subject.** Confetti/sparkles centred on the focal art at large size occlude the very thing being celebrated (the Earth). Place the burst *above/around* the subject and size it smaller (anchor near the subject's top edge minus a gap). (Orbit Launcher: orbit-locked confetti.)
- **JPEG the full-bleed backgrounds:** opaque scene backgrounds need no alpha — convert PNG→JPEG (`sips -s format jpeg -s formatOptions 86`) before bundling. (How Much Can You See: 10 backgrounds 22M PNG → 5.3M JPEG.) Only the transparent sprites stay PNG. Flame `images.load` decodes `.jpg` fine.
- **Don't assume an Earth/planet/horizon sprite is a full-bleed BACKGROUND — it's usually a SUBJECT cutout on a light bg that needs `strip_bg` + transparency.** A manifest role like "curved Earth view" or a name like `earth_curve_day` reads like a backdrop, so it's tempting to JPEG it as a full-bleed bg. But if it's an Earth-on-white/checkerboard cutout, JPEG-ing it **bakes the light bg opaque** — then it can only be hidden by shoving it to the screen edge (its top half would otherwise cover the stars), and anything meant to sit *on* it (a cyclone, a ground-station dish) **floats in the void** because the Earth isn't actually where it looks. Tell which it is by **sampling border-row luminance**: a bright border (mean >200) = light-bg cutout → `strip_bg` to transparency + trim (the trimmed sprite's top edge becomes the visible limb, so you can bottom-anchor it precisely); a dark textured border = true full-bleed → JPEG. (Power Balance: the Earth + a "floating receiver" bug — wrongly JPEG'd a 1672×941 Earth cutout in Phase 1; fixed by `strip_bg` → a transparent 1400×431 horizon, bottom-anchored ~2.8× width with the cyclone/dish ON the disc. A luminance probe — `space(top10%) mean 249` — instantly revealed it was a light-bg cutout, not black space.) For the night/shadow side, if the night sprite has a different framing / baked checkerboard, **drop it and darken the day Earth** via a `ColorFilter.mode(<dark-blue>, BlendMode.modulate)` lerped by the shadow factor.
- **Asset-kit realism:** generated element sprites are often independent single-angle hero renders (mismatched perspective) and any `*_slot_empty` files may be alternate full renders, not decals — pick one canonical base, overlay at tunable anchors, expect a live position-tuning pass.
- **Size overlays/children from the BASE dimension, not the LIVE (zoomed/animated) one.** When a stage element scales (a focus zoom, an idle pulse), deriving a child or screen-space overlay's size from its *current* width inflates it with the zoom (Restore Earth: car + reticle ballooned because they used the zoomed `worldWidth`). Use the un-zoomed base size (`component.size.x`, not `worldWidth`). Screen-space overlays (reticle, target ring) should be base-sized so they never scale with the zoom.
- **Reuse a polished asset across activities:** if another activity already has a premium asset you want (Restore Earth's success tick = the green-check badge from How Much Can You See), **copy it into the new activity's own asset folder** + registry so the module stays self-contained — don't cross-reference another activity's directory. Also judge **mascot legibility on the actual dark stage** — a pack's own mascot can be too dark/low-contrast (Earth Detective's robo set read as near-black on navy); swap in a brighter sibling-pack mascot (we reused Choose-the-Right-Satellite's) copied into the new folder, and **map poses to the situation** (info→guiding, scanning→thinking, wrong→concerned, found→celebrating, finale→happy).
- **Use the provided rich background where the mock shows it — and don't double up its contents.** When a mock shows a specific scene backdrop (a mission-control window with Earth in view), bundle THAT bg (`BoxFit.cover`) instead of the generic house `cosmicBackground`, and DON'T overlay an element the background already contains (Earth Detective: we wrongly floated a separate Earth hologram over a window that already showed Earth). Overlay only what's missing (a satellite + beam), and keep beams/effects terminating ON the subject, not bleeding into adjacent UI.
- **Verify EVERY sprite — filenames lie:** generated packs ship **mislabeled** files. (Restore Earth: `orbit_mascot_idle.png` was a green checkmark, `_celebrate` a starburst — only 2 of 5 mascot files were the mascot.) Eyeball each asset in Phase 0; have a fallback (e.g. reuse the satellite face sprites as the mascot's expressions).
- **`PositionComponent` already has `width`/`height`/`scale` getters.** Declaring `final double width;` on a component shadows `size.x` and trips `annotate_overrides` — name custom fields something else (`diameter`, `beamW`). Same for any built-in field you're tempted to reuse.
- **Mixed-background packs need per-file flood-fill flags.** A single pack often mixes LIGHT-checkerboard sprites (default `strip_bg.py`), dark-bg additive FX (`--min-bright 24 --neutral-tol 34 --min-hole-area …`), and full-bleed rectangular PHOTOS. Never flood-fill a full-bleed photo (cyclone/earth/static-fill) — its own light clouds read as background and get eaten; JPEG those from the originals instead. Auto-classify by sampling border brightness + colour-spread before batching. (Signal Rescue: 46 light + 3 dark-FX + 3 JPEG.)
- **Flame layering:** `camera.backdrop` (behind world) < `world` < `camera.viewport` (HUD on top) — backgrounds go in `backdrop`, never `viewport`. Adding components to the **game root** (no camera world) makes game coords == GameWidget logical pixels, which simplifies Flutter→Flame hit/drop math. Override `backgroundColor() => const Color(0x00000000)` so the Flutter background shows through the `GameWidget`.
- **`images.fromCache` throws on anything not preloaded — preload EVERY sprite any spawn path touches, not just `onLoad`'s.** If `_sprite(p) => Sprite(images.fromCache(...))` and a token-diff/event FX spawns a sprite (`lowPowerGlow` on wrong-use, `dataSuccessBurst` on send) that isn't in the `preload` list, it crashes **the first time that event fires** — `fvm dart analyze` AND `flutter build apk` both pass (it's a runtime cache miss, not a compile error), so only actually triggering the path catches it. Audit every `_sprite(PB.x)` call site against the preload list. (Power Balance.)
- **No emoji in the Flame canvas** — `TextPaint`/canvas don't render colour emoji reliably; use sprites/shapes. (Emoji in *Flutter* `Text` are fine.)
- **Text sizing:** clamp `textScaler` to `TextScaler.noScaling` on the screen so type renders at the designed px regardless of device text-scale.
- **Never drive a voice-paced flow with a fixed-duration `Timer`/`_DelayedCall`.** Voice files are 2–7 s; any hardcoded `Timer(1.7s)` between success→learning or `_DelayedCall(3.6s)` before advancing either cuts a line off mid-word OR leaves silence. The right driver is **`AudioPlayer.onPlayerComplete`** forwarded to the controller. Reach for fixed delays only when the beat is INTENTIONALLY independent of audio (a visual effect timer, a pad-to-burn animation). (Restore Earth.)
- **Muted/blocked audio needs a SHORT reading-time fallback that DEFERS to live audio.** For an auto-sequenced multi-part line (bubble 1 → bubble 2), advance on `onPlayerComplete` (+ a ~350 ms breath) — but a muted user (or web autoplay block) never gets that event and would be stranded on part 1. Arm a ~3.5 s reading-time `Timer` as the no-audio path and have it **skip itself when `voicePlaying` is true** (live narration advances on completion instead). A fixed timer alone fires mid-audio (the original bug); completion alone strands muted users. Make the advance method **idempotent + guarded by scene/text** so timer, audio completion, and the mute handler can all call it safely. (Orbit Launcher: the two-part "fell back" lesson.)
- **Batch-converting ordered VO files: zsh arrays are 1-INDEXED — and always verify the mapping by size.** A bash-style `names=("" "vo_1" …)` loop run in zsh shifts every `scene-N → name` mapping by one (scene-1 landed in a file literally named `.mp3`, and the last scene overwrote it). After ANY ordered batch convert/rename, sanity-check sizes against the script: the shortest line ("Up it goes…") must be the smallest file and the longest line the largest — that check is what caught the shift. (Orbit Launcher.)
- **When deleting code from a state-mutating method, audit what's REQUIRED to remain.** Removing a "timer block" can accidentally take `notifyListeners()` + safety setup with it — state mutates, UI never knows, activity freezes silently with NO error. Always re-read the entire method end-to-end after a delete, and grep for **every cancel/reset call** of state you remove (e.g. when replacing a `List<Timer> _pending` with a single `Timer? _safety`, update `_cancelPending()` call sites). (Restore Earth: deleted the final-monologue Timer loop and accidentally removed `notifyListeners()` → screen stuck on Final 0 forever.)
- **`voiceClip` equality is NOT a replay trigger — bump a `voiceToken` int.** Setting `state.voiceClip = 7` twice in a row (wrong→retry→wrong) won't replay if the screen only diffs the clip number. Pair every `voiceClip:` write with `voiceToken: _state.voiceToken + 1`; screen plays whenever `state.voiceToken != _lastVoiceToken`. Symmetric: init `voiceToken: 1` in the constructor with `_lastVoiceToken = 0` so the **first build also triggers** (zero=zero would silently swallow the intro line).
- **Voice-driven transitions need a safety `Timer` fallback.** Even with `onPlayerComplete` wired, the activity deadlocks if the asset is missing, the device steals audio focus, or the platform drops the complete event (real on Android). Arm a 10–15 s `Timer` whenever the controller queues a voice that DRIVES a transition (success/learning/final 1..N); same handler (`onVoiceFinished`) runs whether real completion or safety fires. Cancel on real completion or any state change. **Also** make `_voice.play(src).catchError((_) => controller.onVoiceFinished())` so a missing asset advances immediately instead of waiting the full safety window. (Restore Earth.)
- **Two `AudioPlayer` instances minimum — one per audio "lane".** SFX (snap/sparkle/burst) on the same player as voice WILL cut Orbit mid-word the moment a sparkle fires. Separate `_sfx` + `_voice`; total cost ~10 KB. Pair with **`_voice.stop()` before every `_voice.play()`** so two close-together lines don't overlap (stop() does NOT fire onPlayerComplete — exactly what you want).
- **Android audio-focus steal: a looping BGM lane DIES the moment another in-app player speaks — and the fix must be PER PLAYER, not global.** `audioplayers` requests audio focus on every `play()` from the player's OWN `AudioContextAndroid` (default `AudioFocus.gain`) — the voice player starting requests full focus, the OS **pauses** the BGM player, and focus-paused players **never auto-resume** (BGM silent forever after the first line). Chrome/desktop have no audio-focus system, so it only reproduces **on the phone**. ⚠️ `AudioPlayer.global.setAudioContext(...)` does NOT fix it: the plugin's `defaultAudioContext` is only **copied into players at create-time** (AudioplayersPlugin.kt `WrappedPlayer(..., defaultAudioContext.copy(), ...)`), and players declared as field initializers are created before any global call lands — so they keep `gain` and the steal continues (symptom: a `resume()` band-aid brings BGM back AFTER the line, but it never plays DURING). The real fix: call **`player.setAudioContext(mix)` on EVERY player** (it awaits creation internally) with `AudioContextAndroid(audioFocus: AndroidAudioFocus.none)` + `AudioContextIOS(category: playback, options: {mixWithOthers})` — `none` means FocusManager never requests focus → all in-app lanes mix; do your own loudness via **setVolume ducking** (e.g. 0.20 → 0.05 in `_playVoice`/`_voiceDone`). On iOS a per-player call just sets the shared session (logged notice, same effect). Sequence: set contexts → then start the BGM loop. Keep `_bgm.resume()` in `_voiceDone` as belt-and-braces. (How Much Can You See BGM — verified against audioplayers_android 5.2.1 source.)
- **Disabled button = dim + `IgnorePointer`, not just dim.** A dimmed-looking CTA that still fires `onTap` is a UX trap (users assume dim = inactive but their taps trigger anyway). When gating a CTA on voice/state, wrap the visual in `IgnorePointer(ignoring: !enabled, child: pill)` so the dim ACTUALLY blocks taps. (Restore Earth Continue button gated on `continueEnabled`.)
- **Adding VO changes GAMEPLAY timing — audit every timed window against the measured clip lengths.** Voice clips run 4–9s; any gameplay window shorter than its narration breaks the loop the moment VO lands: a ~2.7s lock window expires while "Data locked… tap send!" (7.5s) is still playing, and a progress-driven narration (4 transmit lines over an 8s transmission = 2s/line) cuts every clip. Measure durations (`afinfo`) right after the copy step, then: stretch progress-driven phases so each line's window ≥ its clip (+0.5s buffer), and HOLD/freeze state-driven windows (the orbit clock during `dataLocked`) until the child acts. (Signal Rescue.)
- **`AssetSource` paths are relative to `assets/` (audioplayers prefixes it).** A file at `assets/sounds/restore_earth/orbit/orbit_01.wav` is loaded as `AssetSource('sounds/restore_earth/orbit/orbit_01.wav')` — DON'T include the `assets/` prefix or the load 404s silently and `onPlayerComplete` never fires. Add a one-line comment near the call site (this trips people up). And `addPostFrameCallback` your first `play()` from a screen mount — playing before the widget is fully attached fails silently on some devices.
- **Tooling:** use **fvm** (`fvm flutter`/`fvm dart`). `flutter analyze` with **multiple paths crashes** the analysis server — use `fvm dart analyze <single dir>`. `fvm dart analyze lib` shows ~hundreds of pre-existing errors in unreferenced files — those aren't yours.
